# 기획 v2: 가게·건물주 관점 + 확장성 설계

> 위치: `docs/context/owner-and-expansion.md`
> 상태: **초안 (PM 검토 후 확정)**. 각 항목의 `[확정]` 표시가 붙기 전까지 Claude Code는 모델·마이그레이션을 바로 만들지 말고 작업 계획을 먼저 제시한다.
> 기존 문서와 충돌하면 이 문서가 우선한다. 단, 판정 4단계의 **내부 이름**(가능/조건부/어려움/미확인)은 중간발표 자료와 일관성을 위해 바꾸지 않는다.

## 1. 문제 재정의: 이해관계자 4자

기존 기획은 이동약자 한쪽만 봤다. v2는 아래 4자가 모두 얻는 게 있는 구조로 바꾼다.

| 이해관계자 | 우려 | 턱없네가 주는 것 |
|---|---|---|
| 이동약자 (휠체어·유아차·보행 보조기·목발) | 헛걸음, 정보 부재 | 내 조건으로 들어갈 수 있는 곳만 보이는 지도 |
| 가게 사장님 (영업주) | "들어가기 어려운 가게"로 찍혀 손님이 줄어들까 봐 | 반론·보완 정보를 직접 올릴 권리, 잠재 손님 수요 데이터, 무료 경사로 지원사업 연결 |
| 건물주 (임대인) | 건물 구조 문제로 세입자·건물 평판이 나빠질까 봐, 공사 부담 | 가게 책임과 건물 책임을 분리해 표시, 개선하면 건물 내 가게 전체가 좋아지는 효과를 수치로 보여줌 |
| 노원구청 | 경사로 지원사업 대상 발굴이 어려움 | 수요가 있는 가게와 개선 의지가 있는 가게를 데이터로 제공 |

**서비스 포지션 전환**

- v1: 가게마다 들어갈 수 있는지 **판정하는** 지도
- v2: **들어가는 방법**을 알려주고, 못 들어가는 곳은 **개선으로 연결하는** 지도

핵심 문장(발표용): "턱없네는 가게를 평가하지 않습니다. 들어가는 방법을 알려주고, 문턱을 없앨 수 있게 연결합니다."

## 2. 설계 원칙 (모든 기능에 적용)

| ID | 원칙 | 구현 시 의미 |
|---|---|---|
| OP-1 | 가게를 평가하지 않고 사실만 보여준다 | 점수, 순위, 별점, "불량"·"부적합" 같은 단어를 쓰지 않는다. 수치와 사진만 보여준다 |
| OP-2 | 막힌 정보보다 방법을 먼저 보여준다 | 어려움 판정이어도 다른 출입구, 도움 요청 방법, 이동식 경사로 여부를 먼저 보여준다 |
| OP-3 | 사장님에게 응답권이 있다 | 모든 가게 상세에 사장님 코멘트 영역이 있다 (비어 있으면 "사장님이신가요?" 안내) |
| OP-4 | 가게 책임과 건물 책임을 나눈다 | 건물 공용 입구·엘리베이터·공용 화장실은 건물(Building) 정보로 따로 표시한다 |
| OP-5 | 배지는 좋은 쪽으로만 준다 | "개선 완료", "도움 제공 가게" 같은 긍정 배지만 있다. 부정 배지는 만들지 않는다 |
| OP-6 | 나쁜 쪽으로 바뀌는 정보는 검증 후 반영한다 | 판정이 내려가는 제보는 확인되기 전까지 기존 판정을 유지한다 (7장) |
| OP-7 | 돈으로 판정이나 노출을 바꿀 수 없다 | 가게에 과금하는 기능, 유료 상단 노출 기능은 만들지 않는다 (신뢰도 보호) |
| OP-8 | 법 위반 판정이 아니다 | 편의법 수치는 "판정 참고 기준"이다. 소규모 기존 건물은 설치 의무가 없는 경우가 많다는 안내를 사장님 화면과 상세 하단에 넣는다 |

## 3. 표시 정책 v2

### 3.1 판정 문구와 색

내부 enum과 판정 로직은 그대로 두고 **화면 문구와 색만** 바꾼다. 문구는 한 곳(`constants` 또는 설정 파일)에서 관리한다.

| 내부 값 | 기존 표시 | v2 표시 문구 | 색 | 모양 |
|---|---|---|---|---|
| `ACCESSIBLE` (가능) | 가능 | 들어갈 수 있어요 | 초록 | 원 |
| `CONDITIONAL` (조건부) | 조건부 | 도움 받으면 들어갈 수 있어요 | 파랑 | 원 + 손 아이콘 |
| `DIFFICULT` (어려움) | 어려움 | 혼자 들어가기 어려워요 | **회색** (빨강 금지) | 원 |
| `UNKNOWN` (미확인) | 미확인 | 아직 정보가 없어요 · 알려주세요 | 흰색 테두리 | 점선 원 |

- 빨간색은 "위험·금지"로 읽혀 가게에 낙인을 찍으므로 쓰지 않는다.
- 색만으로 구분하지 않고 모양·아이콘을 같이 쓴다 (색약 대응).
- `DIFFICULT` 문구 옆에는 항상 사실 한 줄을 붙인다. 예: "입구 계단 2칸 (약 30cm)".

### 3.2 지도 기본 동작

- 이동 조건을 고르면 기본적으로 `ACCESSIBLE`, `CONDITIONAL`만 지도에 보인다. `DIFFICULT`는 **숨김**이 기본이다.
- "모든 장소 보기"를 켜면 `DIFFICULT`, `UNKNOWN`이 회색·점선으로 보인다.
- 목록 정렬은 거리순이 기본이다. "접근성 낮은 순" 정렬이나 "어려운 가게만 보기" 필터는 **만들지 않는다**.
- 가게·거리 단위의 "접근성 나쁜 곳" 공개 랭킹은 만들지 않는다. 지역 집계는 구청 대시보드(비공개)에서만 쓴다.

## 4. 가게 사장님 기능

### 4.1 가게 인증 (Claim)

| 항목 | 정책 |
|---|---|
| 인증 방법 (해커톤 범위) | 팀 답사 때 가게에 6자리 인증 코드를 전달하고, 사장님이 코드를 입력하면 관리자가 승인한다 |
| 인증 방법 (향후) | 전화 인증, 사업자 정보 확인 |
| 수집하지 않는 것 | 사업자등록번호, 주민등록번호 등 식별번호는 저장하지 않는다 |
| 인증 후 권한 | 코멘트 작성, 도움 제공 선언, 정정 요청, 사장님 대시보드 조회 |
| 인증 없이 불가 | 판정 값 직접 수정 (인증된 사장님도 직접 수정은 불가, 정정 요청만 가능) |

### 4.2 도움 제공 선언과 판정 반영

사장님이 선언할 수 있는 항목:

| 필드 | 타입 | 예 |
|---|---|---|
| `assistance_offered` | bool | 직원이 입장을 도와드려요 |
| `assistance_contact` | text | "입구 호출벨", "전화 02-..." |
| `assistance_hours` | text | "영업시간 내내", "14~17시 제외" |
| `portable_ramp` | bool | 이동식 경사로 보유 |
| `portable_ramp_length_cm` | int | 120 |
| `alt_entrance` | text | "건물 뒤편 주차장 쪽 문은 턱 없음" |
| `owner_comment` | text (200자) | 자유 코멘트 |

판정 반영 규칙 (휠체어·유아차):

| 조건 | 결과 | 근거 |
|---|---|---|
| 입구 단차 ≤ `portable_ramp_length_cm` ÷ 8, 그리고 `assistance_offered`, 그리고 이동식 경사로 사진 확인됨 | `DIFFICULT` → `CONDITIONAL` | 별표 1 12호 경사로 완화(기존시설·1m 이하·상시보조 시 1/8) **준용, 팀 기준** |
| `assistance_offered`만 있고 경사로 없음 | 판정 유지 (`DIFFICULT`), 상세에 도움 요청 방법 표시 | 계단에서 휠체어를 들어 올리는 건 안전 문제로 판정에 넣지 않음 (팀 기준) |
| `alt_entrance`가 있고 그 출입구 정보가 기준 충족 | 대체 출입구 기준으로 판정 | 출입구를 별도 레코드로 저장해 각각 판정 (Entrance 모델, 11장) |

사장님 선언만으로는 판정이 올라가지 않는다. 사진 확인(관리자 또는 다른 사용자 1명)이 있어야 반영된다.

### 4.3 정정 요청

| 단계 | 처리 |
|---|---|
| 요청 | 인증된 사장님이 필드 하나와 새 값, 증빙 사진을 제출 |
| 대기 중 표시 | 기존 값은 유지하고, 해당 필드에 "사장님이 정정을 요청했어요 (확인 중)"을 표시 |
| 반영 | 관리자 승인 또는 다른 사용자 2명 확인 |
| 반려 | 사유를 사장님에게 표시 |
| 기한 | 7일 안에 처리되지 않으면 관리자 알림 |
| 제한 | 같은 필드 정정 요청은 진행 중인 건이 끝나야 새로 가능 |

### 4.4 사진 정책

- 사장님은 입구 사진 **교체 요청**을 할 수 있다 (간판 노출, 직원 얼굴, 오래된 사진 등).
- 가게 정보 **삭제 요청**은 받지 않는다. 입구 구조는 누구나 보는 공개된 물리 정보이기 때문이다. 폐업은 폐업 신고로 처리한다.
- 제보 사진에 사람 얼굴·차량 번호판이 보이면 게시 전 가린다 (MVP는 업로드 안내 + 관리자 검수, 이후 자동 블러).

### 4.5 사장님 대시보드 (가게가 얻는 것)

| 항목 | 설명 | 목적 |
|---|---|---|
| 조건별 조회 수 | "이번 달 유아차 조건으로 42번 조회됐어요" | 이동약자가 잠재 손님이라는 걸 숫자로 보여줌 |
| "가고 싶어요" 수 | 어려움 판정 가게에 이용자가 누른 방문 희망 수 | 개선하면 올 손님이 있다는 신호 |
| 개선 가이드 | 입구 단차에 맞는 이동식 경사로 길이 계산 (단차 × 8) | 사장님이 바로 할 수 있는 조치 |
| 지원사업 안내 | 노원구 경사로 설치 지원사업 링크·문의처 | 비용 부담 해소 (6장) |

## 5. 건물주 관점

### 5.1 가게 정보와 건물 정보 분리

| 정보 | 소속 | 예 |
|---|---|---|
| 건물 공용 출입구, 공용 엘리베이터, 공용 화장실 | `Building` | 2층 가게에 가려면 건물 입구 계단 3칸 |
| 가게 자체 출입구, 가게 내부 단차 | `Place` | 가게 문 앞 턱 3cm |

가게 상세 화면은 "건물 공용 입구"와 "가게 입구"를 **섹션으로 나눠** 보여준다. 건물 구조 때문에 어려운 경우 세입자 책임처럼 보이지 않게 하려는 것이다.

### 5.2 건물주 기능

- 건물주 인증 후 건물 공용 정보에 코멘트와 정정 요청을 할 수 있다 (가게와 같은 절차).
- **개선 시뮬레이션**: "이 건물 입구에 경사로를 설치하면 건물 안 가게 N곳이 휠체어 기준 '들어갈 수 있어요'로 바뀝니다." 판정 엔진에 가상 값을 넣어 다시 계산한 결과를 보여준다.
- 임차 점포가 고정형 경사로를 설치하려면 임대인 동의가 필요한 경우가 있으므로, 시뮬레이션 결과를 사장님이 건물주에게 공유할 수 있는 링크로 제공한다 (Could).

## 6. 개선 연결: 노원구 경사로 설치 지원사업

### 6.1 근거 (지역 문제 적합성)

- 노원구는 법적 설치 의무가 없는 1층 카페·약국·편의점 등 소규모 생활밀착 시설에 경사로를 무료로 설치해 주는 사업을 하고 있고, 경사로 설치 지원 조례도 제정했다 (2025년 보도 기준).
- 2021년 이후 서울시 시민참여예산·복권기금 등으로 148개소를 지원했고, **건물주와 영업주의 의지가 있는 시설을 찾아** 확산하겠다고 밝혔다.
- 다른 자치구(광진·동작·양천·송파)도 비슷한 사업을 하고 있다 → 지역 확장 시 같은 연결 구조를 재사용할 수 있다.

턱없네는 구청이 찾고 있는 "의지 있는 가게"와 "수요가 있는 가게"를 데이터로 보여줄 수 있다. 가게 입장에서는 정보 공개가 곧 **무료 개선의 입구**가 된다.

### 6.2 개선 선순환 흐름

```
어려움 판정 가게
  → 이용자 "가고 싶어요" 누적 (수요 신호)
  → 사장님 대시보드에 수요 표시 + 지원사업 안내
  → 사장님/건물주가 구청 지원사업 신청 (외부)
  → 설치 후 "개선 완료" 제보 (사진)
  → 재판정 → "개선 완료" 배지 부여
  → "가고 싶어요"를 누른 이용자에게 알림
```

### 6.3 정책

- 턱없네는 지원사업을 **대신 신청하지 않는다**. 안내와 연결만 한다 (링크, 문의처, 필요한 정보 정리).
- 지원사업 정보(대상, 기간, 문의처)는 코드에 하드코딩하지 않고 관리자 화면에서 수정할 수 있는 데이터로 둔다 (매년 바뀌기 때문).
- "개선 완료" 배지는 판정이 한 단계 이상 올라간 날로부터 계속 유지된다. 이후 판정이 다시 내려가면 배지만 숨긴다.

## 7. 악성 제보·분쟁 방지

가게 매출과 연결되므로 경쟁 업체의 악의적 제보, 반대로 가게의 과장된 정보를 모두 막아야 한다.

| 상황 | 정책 |
|---|---|
| 판정이 **내려가는** 제보 (예: 가능 → 어려움) | 로그인과 사진이 필수. 단일 제보는 `PENDING` 상태로 두고 기존 판정 유지 + "새 제보 확인 중" 표시. 다른 사용자 2명 확인 또는 관리자 승인 시 반영 |
| 판정이 **올라가는** 제보 (예: 어려움 → 가능) | 사진 필수. 1명 확인 또는 관리자 승인 시 반영 (이동약자가 헛걸음할 위험이 있으므로 확인 없이 반영하지 않음) |
| 같은 사용자의 같은 장소 반복 제보 | 24시간에 1회 |
| 가입 7일 미만 계정의 판정 하향 제보 | 관리자 검수 큐로 보냄 |
| 한 사용자가 특정 가게들에 판정 하향 제보를 반복 | 관리자 알림 (규칙: 7일 안에 서로 다른 장소 5곳 이상 하향 제보) |
| 사장님 선언과 사용자 제보가 충돌 | 사진 증빙이 있는 최신 값을 우선, 둘 다 있으면 관리자 판단. 판단 전까지 "정보가 서로 달라요, 방문 전 전화 확인을 권해요" 표시 |

## 8. 확장성 설계 (사업 확장 ↔ 코드 구조)

피드백 F4 대응. 사업 확장 계획마다 **지금 코드에 어떤 구조를 미리 넣어 두는지** 연결한다. 발표에서 이 표를 그대로 보여준다.

| 사업 확장 | 필요한 구조 | 해커톤에서 할 일 |
|---|---|---|
| 지역 확장 (월계1동 → 노원구 → 서울 자치구) | `Region` 모델, 모든 장소 쿼리에 region 스코프, 지역 경계 GeoJSON | 모델과 스코프 적용. 데이터는 월계1동 하나 |
| 이동 조건 추가 (캐리어, 시각장애, 고령 보행 등) | 판정 규칙을 **코드 if문이 아닌 데이터**(`ConditionProfile`, `Rule`)로 저장, 규칙 버전 관리 | 규칙 테이블 + 판정 엔진. 새 조건 추가가 DB 행 추가만으로 되는지 테스트로 증명 |
| 장소 유형 확장 (가게 → 병원, 주민센터, 버스정류장) | `Place.category`, 접근성 필드 정의 테이블(`FieldDefinition`) | 필드 키를 자유 텍스트가 아닌 FK로 (ERD 지적 사항 해결) |
| 다른 자치구 지원사업 연결 | 지원사업 정보를 `Region`별 데이터로 관리 | 관리자 화면에서 수정 가능하게 |
| 데이터 개방 · 구청 협력 (B2G) | 읽기 전용 공개 API `/api/v1/`, GeoJSON·CSV 내보내기 | DRF 읽기 API + 내보내기 1종 |
| 구청 대시보드 | 집계 쿼리 (지역별 판정 분포, "가고 싶어요" 상위 가게, 개선 완료 수) | Could |
| 지도 SDK 교체 (카카오 → 다른 지도) | 프론트 지도 호출을 어댑터 한 곳으로 모음 | 카카오맵 호출 코드를 한 모듈로 분리 |

**규칙 버전 관리**

- `RuleSet(version, is_active, created_at)` 아래에 `Rule`들이 속한다.
- 판정 결과(`Judgment`)에 `rule_version`을 저장한다.
- 규칙이 바뀌면 전체 재판정 명령(management command)으로 다시 계산한다.
- 모든 `Rule`에 근거 구분 `basis`(`LAW` 법령 / `APPLIED` 준용 / `TEAM` 팀 기준)을 저장해 화면과 문서에서 근거를 보여준다.

## 9. 비즈니스 모델 (초안)

| 대상 | 가치 | 수익 구조 |
|---|---|---|
| 이동약자 | 헛걸음 없는 외출 | 무료 |
| 가게·건물주 | 잠재 손님 데이터, 무료 개선 연결, 긍정 배지 | **무료** (OP-7: 가게 과금 없음) |
| 자치구 (B2G) | 경사로 지원사업 대상 발굴, 설치 후 실제 이용 데이터(사후 관리), 접근성 실태 데이터 | 데이터 제공·실태조사 협약 |
| 프랜차이즈·기업 (ESG) | 점포 접근성 현황 리포트 | 리포트 제공 |

가게에서 돈을 받지 않는 이유: 돈을 내면 판정이 좋아진다는 의심이 생기는 순간 이용자 신뢰가 무너진다. 수익은 데이터를 필요로 하는 기관에서 낸다.

## 11. 데이터 모델 변경 (ERD 델타)

기존 모델과 이름이 다를 수 있다. Claude Code는 **기존 models.py와 비교한 변경 계획을 먼저 제시**하고, 승인 후 마이그레이션을 만든다.

| 모델 | 주요 필드 | 비고 |
|---|---|---|
| `Region` | name, code, boundary(GeoJSON) | 신규 |
| `Building` | region FK, address, lat, lng | 신규. 공용 접근성 값은 `AccessibilityValue`로 연결 |
| `Place` | region FK, building FK(null), name, category | 기존 가게 테이블에 FK 추가 |
| `Entrance` | place FK 또는 building FK, is_main, description | 신규. 대체 출입구 판정용 |
| `FieldDefinition` | key(PK), label, unit, scope(`PLACE`/`BUILDING`/`ENTRANCE`), value_type | 신규. 필드 키 자유 텍스트 문제 해결 |
| `AccessibilityValue` | target, field FK, value, source(`TEAM_SURVEY`/`USER_REPORT`/`OWNER`/`AI`), status(`VERIFIED`/`PENDING`), photo, created_by | 기존 값 테이블 확장 |
| `ConditionProfile` | key(`WHEELCHAIR`/`STROLLER`/`WALKER`/`CRUTCH`), label | 신규 |
| `RuleSet` | version, is_active | 신규 |
| `Rule` | rule_set FK, profile FK, field FK, operator, threshold, outcome, basis(`LAW`/`APPLIED`/`TEAM`), note | 신규 |
| `Judgment` | place FK, profile FK, result, rule_version, computed_at | 판정 캐시 |
| `OwnerClaim` | user FK, place 또는 building FK, role(`OPERATOR`/`BUILDING_OWNER`), status, verified_by | 신규 |
| `OwnerResponse` | place FK, 4.2의 필드들 | 신규 |
| `CorrectionRequest` | target, field FK, proposed_value, evidence_photo, status, reason, requested_by | 신규 |
| `VisitWish` | user FK, place FK, profile FK, created_at | 신규. 사용자당 장소·조건별 1회 |
| `SupportProgram` | region FK, title, target_desc, period, contact, url, is_active | 신규. 지원사업 안내 |

## 12. Claude Code 작업 규칙 (이 문서 관련)

1. 모델·마이그레이션 변경 전에 변경 계획(추가/수정/삭제 목록)을 먼저 보여주고 승인을 받는다.
2. 판정 4단계 내부 enum 이름은 바꾸지 않는다. 화면 문구는 상수 한 곳에서 관리한다.
3. 판정 로직에 if문으로 조건별 기준을 박지 않는다. 기준값은 `Rule` 데이터에서 읽는다.
4. 판정이 바뀌는 로직(제보 반영, 사장님 선언 반영, 경계값)에는 단위 테스트를 같이 작성한다. 경계값 예: 단차 2cm / 2.1cm, 단차 = 경사로 길이 ÷ 8.
5. OP-7 위반 기능(과금, 유료 노출, 공개 랭킹)은 요청이 있어도 만들기 전에 PM에게 확인한다.
6. 지원사업, 판정 문구처럼 매년·자주 바뀌는 정보는 하드코딩하지 않는다.
7. 사업자등록번호 등 식별번호 입력 필드를 만들지 않는다.
